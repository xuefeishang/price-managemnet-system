# 通知管理平台当前实现状态

更新时间：2026-06-10

## 文档职责

本文是通知管理平台“当前已经实现什么、还缺什么、审计发现什么风险”的唯一事实源。状态必须以当前代码、数据库迁移和最近一次验证结果为准。

- 目标设计与历史决策：见 [notification-management-platform-feature.md](notification-management-platform-feature.md)
- 尚未闭环工作的实施计划：见 [notification-management-platform-closure-feature.md](notification-management-platform-closure-feature.md)

状态口径：

- `[x]`：代码已实现，并存在本地自动化验证或明确代码证据。
- `[~]`：主体代码已实现，但仍缺生产等价环境、真实外部平台验证或规模验证。
- `[ ]`：尚未实现。

本次审计口径：基于 2026-06-10 当前代码、`init.sql`、Flyway 迁移、前端 API 调用和测试文件进行核验；真实微信平台、真实 MySQL 压测和生产环境权限/日志不在本地静态审计中自动视为完成。

## 当前结论

通知管理平台的站内消息、Outbox、管理后台、系统公告、微信小程序订阅消息代码链路和 PC 运维主体已经实现。四期“通讯管理/小程序订阅运维”不能仅凭页面按钮和本地构建宣称 9.5+ 完整闭环，剩余门槛集中在：

1. 微信真实模板、真实授权、真实投递、正式公告触达和点击跳转仍缺联调证据。
2. 真实 MySQL 的索引命中、分页性能、Outbox 并发领取和大数据量验证仍缺记录。
3. 生产角色授权、按钮显隐、后端拒绝行为和历史敏感日志仍缺上线环境复核记录。
4. “跟进任务”尚未实现，当前只有用户级 `followUpRequired` 跟进标记。
5. 批量授权引导、投递审计详情和渠道模板维护仍有可用性/规模化增强空间。

## 审计发现的问题和隐患

| 编号 | 严重度 | 问题/隐患 | 影响 | 解决方案 |
| --- | --- | --- | --- | --- |
| R-001 | 高 | 真实微信联调证据缺失，代码已接入 Provider 但没有真实 token、模板、授权、投递、跳转闭环记录 | 无法证明小程序订阅消息在生产账号可用 | 执行 WX-01 至 WX-05，并将 evidence 归档 |
| R-002 | 高 | 测试投递会真实调用微信接口并消耗用户一次订阅授权 | 误用真实业务用户会降低授权余额，影响后续正式触达 | 只允许测试账号执行；PC 二次确认保留；后续可增加“测试用户白名单”或测试投递权限审批 |
| R-003 | 高 | 真实 MySQL Explain 和并发 Outbox 验证缺失 | 本地测试不能证明大数据量和多实例 worker 下性能与幂等可靠 | 执行 DB-01 至 DB-04，归档 SQL、数据规模和指标 |
| R-004 | 高 | 生产角色权限尚未复核 | 可能出现低权限账号能远程校验 token、测试投递或处理订阅异常 | 执行 OPS-01，用不同角色账号验证前端按钮和后端 `@PreAuthorize` |
| R-005 | 中高 | 历史敏感日志只通过迁移清理了部分 `operation_log.request_params`，没有覆盖备份、导出、代理日志和应用日志 | AppSecret、access_token、OpenID 仍可能存在历史介质中 | 执行 OPS-02，形成脱敏巡检记录 |
| R-006 | 中高 | 批量授权引导 `sendGuide` 仍通过 `targetUsers()` 全量加载活跃用户再内存过滤 | 用户量增长后会产生内存和响应时间风险，也不利于发送明细审计 | 改为数据库分页筛选或后台任务批处理，并记录批次结果 |
| R-007 | 中 | 订阅资格快照为最终一致，模板配置变化或事件遗漏时可能短暂显示旧状态 | PC 订阅授权列表可能短时间不准确 | 已有应用启动、配置变化和定时重建；后续增加“刷新中/配置指纹不一致”提示和手动重建入口 |
| R-008 | 中 | `V34` 先在订阅授权表增加异常处理列，`V35/V36` 又迁移到独立处理表并删除旧列 | 迁移顺序或半执行环境需要特别确认，避免上线执行失败 | 发布前在空库、旧库和预发库完整跑 Flyway；保留迁移顺序说明，不手工跳过 V34 |
| R-009 | 中 | 渠道模板维护允许手工输入通知类型和字段映射 | 容易输入不存在的通知类型、重复映射或错误字段名，导致运行时跳过/失败 | 执行 UX-01，使用字典下拉、唯一校验和字段映射校验 |
| R-010 | 中 | 投递审计详情当前主要围绕选中消息查看，日志筛选存在前端过滤边界 | 大量投递日志或跨消息错误定位时效率不足 | 执行 UX-03，新增后端投递日志分页和错误码筛选 |
| R-011 | 中 | `FOLLOW_UP` 只是跟进标记，不是任务系统 | 管理员可能误以为系统已生成可分派、可闭环的任务 | 文案统一为“跟进标记”；若业务需要任务，执行 TASK-01 |
| R-012 | 低 | 页面按钮 icon 仍存在字符符号混用 | 与此前 UI 统一要求不完全一致，影响专业一致性 | 执行 UI-01，统一按钮图标组件和右侧操作区样式 |

## 状态纠偏记录

- N-003 的正确实现描述是“分页 recipient 后批量查询 message”，不是“join DTO 分页”。
- N-017、N-018 的代码实现已经存在，不再标记为未开始；真实微信联调作为独立验证项跟踪。
- “生成跟进任务”统一改称“设置跟进标记”；在真实任务模型落地前，不得宣称已生成任务。
- 远程 token 校验、隔离测试投递和异常处理已完成代码主体，不再在后续章节写作“待开发”；但真实微信证据仍未闭环。
- N-025/A-10 已通过资格快照和数据库 JOIN 分页完成代码闭环；快照只服务管理查询，真实投递继续读取原始授权记录。
- 四期当前结论应表述为“运维主体已实现，外部联调、规模验证和生产复核未闭环”，不得仅通过评分文字宣称 9.5+ 完成。
