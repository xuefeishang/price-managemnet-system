# 菜单层级与顶部导航重构方案

## Context

当前 PC 端布局中，左侧菜单和页面上方导航存在职责重叠：

- 左侧菜单已经展示一级、二级、三级菜单。
- 页面顶部 `sub-navbar` 又展示当前一级菜单下的二级菜单。
- 对于 `基础运维 > 字典管理 > 产地管理/客户管理/数据字典` 这类结构，顶部区域更适合承载三级导航，而不是重复二级入口。
- `style-settings` 页面中的 `总览/品牌/色彩/排版/布局/首页体验/分类视觉/版本` 当前放在页面内部左侧导航中，占用了配置工作台空间，需要重新布局。

本次方案目标是明确系统菜单树和页面内部导航的边界，并重构 PC 端导航布局：

1. 左侧菜单必须完整展示当前用户可见的系统菜单树。
2. 页面顶部只展示当前分支的下级内容，不再重复展示二级菜单。
3. 三级菜单以顶部 Tab 形式展示。
4. 四级及更深层级收纳在对应三级 Tab 内。
5. 无 `path` 菜单默认只作为分组，不触发顶部导航展示。
6. `style-settings` 等复杂工作台页面需要取消内部占位式侧栏导航，将配置域导航整合到更合理的位置。

## 实现方案

### 1. 菜单职责划分

#### 左侧菜单：完整系统目录

左侧菜单承担全局导航职责，规则如下：

- 展示 `visibleMenus` 中所有可见菜单层级。
- 支持一级、二级、三级、四级及更深层级。
- 有 `path` 的菜单点击后跳转。
- 无 `path` 且有子菜单的菜单点击后展开/收起。
- 当前路由所在的父链需要自动展开。
- 当前路由对应菜单节点需要高亮。

示例：

```text
基础运维
  分类管理
  导入导出
  字典管理
    产地管理
    客户管理
    数据字典
```

#### 页面顶部导航：当前分支下级导航

顶部导航承担局部上下文切换职责，规则如下：

- 不展示当前一级菜单下的二级入口集合。
- 当当前二级菜单存在子菜单时，顶部展示这些子菜单。
- 如果顶部展示的三级菜单还有子菜单，点击该三级 Tab 后以下拉方式展示四级菜单。
- 如果当前页面没有下级菜单，顶部导航隐藏。
- 如果当前点击的是无 `path` 分组菜单，且没有发生实际路由跳转，顶部导航隐藏。

示例：

```text
基础运维 > 字典管理

顶部 Tab：
产地管理 | 客户管理 | 数据字典
```

四级示例：

```text
系统管理
  样式设置
    品牌
      Logo 设置
      系统名称
```

顶部显示：

```text
品牌 v | 色彩 | 排版

品牌下拉：
Logo 设置
系统名称
```

### 2. 页内导航边界与 `style-settings` 重构

`style-settings` 页面现有的 `总览/品牌/色彩/排版/布局/首页体验/分类视觉/版本` 目前由页面内部左侧导航承载。该导航与系统左侧菜单形成“双左侧导航”，同时压缩中央配置区和右侧预览区，使用体验不理想。

本次改造需要将 `style-settings` 纳入专项布局优化，但暂不把这些配置域写入后端 `menu_item` 表。

目标布局：

- PC 端取消 `StyleSettingsShell` 内部左侧 section nav。
- 配置域导航上移到页面内容顶部，视觉上复用系统顶部上下文导航的 Tab 样式。
- 工作台主体改为两栏：主配置区 + 实时预览区。
- 顶部状态栏保留页面标题、当前方案摘要、保存状态和唯一正式生效入口“保存配置”按钮。
- 移动端继续使用横向滚动 Tab，但放在状态栏下方，不使用侧栏。
- `总览/品牌/色彩/排版/布局/首页体验/分类视觉/版本` 作为页面本地 section 配置，不参与菜单权限，也不要求管理员在菜单配置中维护。

推荐状态同步方式：

- 打开 `/style-settings` 默认进入 `overview`。
- 点击 `品牌`、`色彩` 等配置域 Tab 只切换 `activeSection`，不刷新页面。
- 使用 `?section=brand` 或 `#brand` 持久化当前配置域，刷新后恢复。
- 切换配置域不触发未保存确认；只有离开 `/style-settings` 页面时触发未保存确认。
- 顶部系统上下文导航和 `style-settings` 配置域导航可以共享组件样式，但数据来源不同：前者来自菜单树，后者来自页面本地 section 配置。

后续如果需要升级为真实菜单，需要同时满足：

- 拆分为独立路由，例如 `/style-settings/brand`。
- 菜单配置中新增对应节点。
- 路由守卫、权限、文档同步更新。
- 页面内部状态支持跨路由保留或恢复。

### 3. 前端技术设计

#### 3.1 统一菜单树解析

当前 `Layout.vue` 同时兼容 `children` 嵌套结构和 `parentId` 扁平结构，后续应集中为统一计算逻辑。

建议新增以下计算方法：

```typescript
type MenuNode = MenuItem & {
  children?: MenuNode[]
}

const menuTree = computed<MenuNode[]>(() => normalizeMenuTree(menuStore.visibleMenus))
```

`normalizeMenuTree` 需要：

- 如果后端已返回树结构，按 `sortOrder` 递归排序。
- 如果后端返回扁平结构，通过 `parentId` 组装为树。
- 避免直接修改后端返回对象，防止排序副作用污染 store。

#### 3.2 当前菜单定位

根据当前路由找到菜单节点及父链：

```typescript
interface MenuMatch {
  node: MenuNode
  ancestors: MenuNode[]
}

const currentMenuMatch = computed<MenuMatch | null>(() => {
  return findMenuByPath(menuTree.value, route.path)
})
```

匹配规则：

- 优先精确匹配 `menu.path === route.path`。
- 对编辑页、详情页等非菜单路由，可按 `route.meta.activeMenu` 或最长 path 前缀回退。
- 若找不到匹配菜单，顶部导航隐藏，左侧只保留一级状态。

建议后续为编辑/详情类路由补充 `meta.activeMenu`：

```typescript
{
  path: 'product-edit/:id?',
  meta: {
    title: '产品维护',
    editorOnly: true,
    activeMenu: '/products'
  }
}
```

#### 3.3 左侧递归菜单

将当前写死到三级的模板重构为递归渲染。

建议拆分组件：

```text
frontend/src/components/layout/SidebarMenuTree.vue
frontend/src/components/layout/SidebarMenuItem.vue
```

组件职责：

- `SidebarMenuTree.vue`：接收 `menus`、`currentPath`、`expandedIds`。
- `SidebarMenuItem.vue`：渲染单个菜单节点，并递归渲染子节点。
- 展开状态由父组件统一管理。

样式规则：

- 一级菜单保留图标。
- 二级及以后使用缩进和更轻的字体权重。
- 缩进按层级递增，但设置最大缩进，避免深层级过度挤压。
- 当前路由父链保持展开。

#### 3.4 顶部上下文导航

顶部导航组件建议拆分为：

```text
frontend/src/components/layout/ContextSubNav.vue
```

输入：

```typescript
interface ContextSubNavProps {
  parent?: MenuNode
  items: MenuNode[]
  activePath: string
}
```

计算顶部展示内容时必须先明确菜单深度：

```typescript
const depth = match.ancestors.length + 1
```

深度定义：

| 深度 | 示例 | 顶部导航 |
|------|------|----------|
| 1 | `首页`、`基础运维` | 隐藏 |
| 2 | `产品管理 > 产品列表` | 若当前二级无子菜单则隐藏；若有子菜单则展示其子菜单 |
| 3 | `基础运维 > 字典管理 > 产地管理` | 展示当前二级菜单的全部子菜单，也就是三级 Tab |
| 4+ | `系统管理 > 样式设置 > 品牌 > Logo 设置` | 仍展示当前二级菜单的子菜单，也就是三级 Tab；四级收在对应三级 Tab 下拉中 |

计算顶部展示内容：

```typescript
const contextSubNav = computed(() => {
  const match = currentMenuMatch.value
  if (!match) return null

  const chain = [...match.ancestors, match.node]
  const depth = chain.length

  // 一级菜单不展示顶部导航。
  if (depth <= 1) return null

  // 二级菜单：只有当前二级本身有子菜单时，顶部展示三级。
  if (depth === 2) {
    if (!match.node.children?.length) return null
    return {
      parent: match.node,
      items: match.node.children
    }
  }

  // 三级及以后：顶部始终展示二级菜单的子菜单，也就是三级 Tab。
  const secondLevelMenu = chain[1]
  if (secondLevelMenu?.children?.length) {
    return {
      parent: secondLevelMenu,
      items: secondLevelMenu.children
    }
  }

  return null
})
```

这条规则可以避免重复二级菜单：

- 当前页面是二级菜单时，如果没有子菜单，顶部隐藏。
- 当前页面是三级菜单时，顶部展示同组三级菜单。
- 当前页面是四级菜单时，顶部展示三级菜单，四级收在对应三级项内。
- 点击无 `path` 分组菜单但没有实际路由变化时，无法形成页面上下文，顶部隐藏。

#### 3.5 四级及以后交互

顶部三级项有子菜单时，使用点击下拉，而不是 hover 或第二行展开。

规则：

- 顶部 Tab 本身如果有 `path`，点击 Tab 跳转。
- 顶部 Tab 如果无 `path` 且有子菜单，点击展开下拉。
- 顶部 Tab 如果既有 `path` 又有子菜单，点击文字区域跳转，点击右侧箭头展开下拉；如果实现复杂，第一期统一点击展开下拉，菜单内提供“进入本页”项。
- 下拉项使用点击触发跳转，不使用 hover 作为主要交互。
- 下拉最多展示到四级；更深层级通过左侧完整树访问。
- 超过四级的菜单仍应通过左侧完整树访问，顶部只承接当前上下文的常用切换。

下拉交互状态：

| 操作 | 行为 |
|------|------|
| 点击有下级的三级 Tab | 展开下拉 |
| 再次点击同一三级 Tab | 收起下拉 |
| 点击其他三级 Tab | 关闭旧下拉，执行新 Tab 行为 |
| 点击页面空白处 | 收起下拉 |
| 按 Esc | 收起下拉 |
| 点击下拉四级项 | 跳转到对应路由并收起下拉 |

### 3.6 无 path 菜单行为

无 `path` 菜单是分组节点，不代表页面。

| 场景 | 行为 |
|------|------|
| 左侧点击无 `path` 且有子菜单的菜单 | 只展开/收起左侧树，不跳转 |
| 无 `path` 菜单被展开后 | 内容区保持当前页面，不强制进入第一个子菜单 |
| 无 `path` 菜单没有实际路由上下文 | 顶部导航不展示 |
| 当前路由位于该无 `path` 菜单的子孙节点 | 顶部按当前实际路由计算并展示对应三级 Tab |

### 4. 后端与数据库设计

本次前端导航重构不需要改数据库表结构。

但需要修复一个初始化逻辑问题：

```java
createMenuItem(basicMgmt, "字典管理", null, "dict", 5, true, ...);
MenuItem dictMgmt = menuItemRepository.findByPath("/dict").orElse(null);
```

`字典管理` 的 `path` 为 `null`，后续用 `/dict` 查询会失败，导致 Java 初始化流程下三级菜单可能不会被创建。

建议改为直接接收创建结果：

```java
MenuItem dictMgmt = createMenuItem(basicMgmt, "字典管理", null, "dict", 5, true, ...);
createMenuItem(dictMgmt, "产地管理", "/origins", null, 1, true, ...);
createMenuItem(dictMgmt, "客户管理", "/customers", null, 2, true, ...);
```

如果本次只做前端导航重构，该修复可作为同批次的小后端修复提交；不涉及表结构变更。

## 实现步骤

### Phase 1：菜单树工具函数

1. 新增菜单树工具或在 `Layout.vue` 内先局部实现：

1. 抽出递归菜单组件。
2. 左侧菜单改为递归渲染，不再写死一级、二级、三级。
3. 根据当前路由自动展开父链。

5. 点击有 path 节点时跳转并保持父链展开。

### Phase 3：顶部上下文导航

1. 抽出 `ContextSubNav` 组件。
2. 删除顶部重复展示二级菜单的逻辑。
3. 顶部只展示：
   - 当前二级菜单的子菜单；
   - 或当前三级/四级所在二级菜单的子菜单；
   - 无可展示项时隐藏。
4. 三级项下存在四级时，使用下拉收纳。
5. 点击无 `path` 分组菜单时，只改变左侧展开状态，不改变顶部导航。

### Phase 4：`style-settings` 页面布局重构

1. 从 `StyleSettingsShell.vue` 中移除 PC 内部左侧 `section-nav`。
2. 新增或复用顶部 Tab 组件展示配置域：
   - 总览

   - 色彩
   - 排版
   - 布局
   - 首页体验
   - 分类视觉

3. PC 主体布局改为两栏：
   - 左侧：配置区，承载当前 section 面板。
   - 右侧：实时预览区，保持 sticky。
4. 状态栏保留保存状态和操作按钮，但高度需要压缩，避免与配置域 Tab 叠加后占用过多首屏。
5. 使用 `?section=` 或 hash 同步 `activeSection`，刷新后恢复当前配置域。
6. 切换 section 不触发未保存确认；离开 `/style-settings` 时继续触发确认。
7. 移动端保持横向 section Tab，预览继续使用抽屉或折叠面板。

## 风险与控制

| 风险 | 影响 | 控制方式 |
|------|------|----------|
| 菜单返回结构不稳定 | 左侧或顶部计算错误 | `normalizeMenuTree` 同时兼容树结构和扁平结构 |
| 深层级菜单样式挤压 | 左侧可读性下降 | 设置最大缩进，深层使用更紧凑样式 |
| 编辑/详情页找不到菜单 | 高亮和顶部导航丢失 | 补充 `route.meta.activeMenu` |
| 顶部导航承载过多 | 横向溢出 | 顶部仅展示当前分支下一级，四级使用下拉 |
| 页内 Tab 被误纳入系统菜单 | 状态管理复杂 | 明确页内导航与菜单树边界 |
| `style-settings` 顶部区过高 | 首屏配置空间不足 | 状态栏压缩高度，配置域 Tab 与状态栏分层但保持紧凑 |
| `style-settings` section 同步到 URL 后污染浏览历史 | 返回行为不符合预期 | section 切换使用 `router.replace`，不使用 `push` |
| 移动端回归 | 移动菜单异常 | PC 递归组件先隔离实现，移动端单独回归 |

## 决策点

### 决策点 1：顶部导航是否显示二级菜单

结论：不显示。

原因：

- 左侧已经完整展示二级菜单。
- 顶部重复二级入口造成信息重复。
- 顶部空间更适合当前模块内的下级切换。

### 决策点 2：`style-settings` 页内分区是否纳入菜单树

结论：暂不纳入后端菜单树，但必须重构页面内部布局。

原因：

- 当前不是独立路由。
- 属于同一个配置工作台中的局部导航。
- 保持页面内状态和草稿配置更稳定。
- 现有内部左侧导航体验不佳，应迁移为内容顶部配置域 Tab，并释放工作台横向空间。

### 决策点 3：四级菜单如何展示

结论：点击顶部三级 Tab 后下拉收纳，左侧完整展示。

原因：

- 顶部横向空间有限。
- 四级属于三级上下文内的细分动作。
- 左侧完整树可作为兜底导航。

### 决策点 4：无 path 菜单是否自动跳转

结论：不自动跳转。

原因：

- 无 `path` 菜单是分组，不代表页面。
- 自动跳第一个子菜单会制造隐式导航，用户容易误解。
- 没有实际路由时不展示顶部导航，可以让页面状态更可预测。

## 验收标准

1. 左侧菜单可以完整展示所有可见菜单层级。
2. 顶部导航不再重复展示一级菜单下的二级入口。
3. 进入三级菜单分组时，顶部展示同组三级 Tab。
4. 四级菜单能在顶部三级项内收纳展示。
5. 点击无 `path` 菜单只展开/收起左侧树，不跳转，不单独触发顶部导航。
6. `style-settings` 页面内部不再保留 PC 左侧 section nav，配置域改为顶部 Tab。
7. `style-settings` 切换配置域不触发未保存确认，刷新后可恢复当前配置域。
8. 菜单权限不被绕过，未授权菜单不会出现在左侧或顶部。
9. 编辑页、详情页能正确回落到对应主菜单高亮。
10. PC 与移动端布局无明显视觉回归。
