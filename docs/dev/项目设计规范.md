## 一、统一文字管理

### 1.1 核心原则：禁止硬编码

**所有编码值的显示名称必须从字典服务动态获取，严禁在前端代码中硬编码中文标签。**

### 1.2 字典服务架构

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│   sys_dict 表   │────►│  SysDictService │────►│   useDict.ts    │
│  (数据源)       │     │  (后端服务)     │     │  (前端缓存)     │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

### 1.3 字典数据结构

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| category | VARCHAR(50) | 字典分类 | `currency` |
| dictKey | VARCHAR(100) | 字典键 | `CNY` |
| dictValue | VARCHAR(200) | 显示值 | `人民币` |
| extraValue | TEXT | 扩展值 | `¥` / JSON配置 |
| sortOrder | INT | 排序 | `1` |
| status | VARCHAR(20) | 状态 | `ACTIVE` |

### 1.5 前端使用规范

**正确示例：**

```vue

  loadAllDicts() // 必须调用，加载字典缓存

  <!-- 状态显示 -->

    <option v-for="opt in getDictOptions('user_role')" :key="opt.value" :value="opt.value">
      {{ opt.label }}
    </option>
  </select>

  <!-- 货币符号 -->

</template>
```

**禁止示例：**

```vue

```

### 1.6 后端使用规范

```java
// 字典服务注入
@Service
@RequiredArgsConstructor
public class MyService {
    private final SysDictService sysDictService;

    public String getStatusLabel(String status) {
        return sysDictService.getDictByCategoryAndKey("common_status", status)
            .map(SysDict::getDictValue)
            .orElse(status);
    }
}
```

### 1.7 新增字典流程

1. **数据库插入**：在 `sys_dict` 表新增记录
2. **前端分类标签**：在 `useDict.ts` 的 `CATEGORY_LABELS` 添加分类中文名
3. **便捷方法**：如需要，在 `useDict.ts` 添加便捷方法（如 `getXxxLabel`）
4. **页面使用**：通过 `getDictValue` 或便捷方法获取显示值

## 二、统一功能模块

### 2.1 功能模块结构

每个功能模块遵循统一的三层架构：

```

├── 后端
```

### 2.2 RESTful API 规范

| 操作 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 列表查询 | GET | `/api/xxx` | 分页参数：`page`, `size` |

### 6.4 动态适配规范

**核心原则：优先动态适配，避免静态硬编码。**

所有涉及数量、颜色、配置项的渲染，必须优先考虑动态适配，而非静态写死。

#### 6.4.1 动态渲染优先

| 场景 | 禁止写法 | 正确写法 |
|------|----------|----------|
| 列表渲染 | 写死固定数量的元素 | 使用 `v-for` 动态渲染 |
| 颜色显示 | 写死颜色值 | 使用 CSS 变量或 props |
| 配置项数量 | 固定 N 个配置项 | 根据数据源动态生成 |

**示例：图表色板**

```vue
<!-- ❌ 禁止：固定 6 个元素 -->
<div class="chart-bar color-1"></div>
<div class="chart-bar color-2"></div>
<div class="chart-bar color-3"></div>
<!-- ... -->

<!-- ✅ 正确：动态渲染 + CSS 变量 -->
<div
  v-for="idx in chartColorCount"
  :key="idx"
  class="chart-bar"
  :style="{
    background: `var(--chart-color-${idx})`,
    height: `${baseHeight + (idx - 1) * step}px`
  }"
></div>
```

#### 6.4.2 CSS 变量与动态渲染结合

当需要同时满足"实时响应"和"动态适配"时，采用以下模式：

```vue
<template>
  <!-- 动态渲染数量，CSS 变量控制颜色 -->
  <div
    v-for="idx in itemCount"
    :key="idx"
    :style="{ color: `var(--dynamic-color-${idx})` }"
  >
    {{ items[idx - 1] }}
  </div>
</template>
```

**优势：**
- 数量由数据源决定，后端扩展无需改前端
- 颜色由 CSS 变量控制，切换主题实时生效

#### 6.4.3 运维扩展友好

| 维度 | 静态实现 | 动态实现 |
|------|----------|----------|
| 后端新增配置项 | 需改前端代码 | 自动适配 |
| 配置项数量变化 | 需改前端代码 | 自动适配 |
| 颜色/样式变化 | 需改前端代码 | CSS 变量自动生效 |

**检查清单：**

- [ ] 列表/数组类数据使用 `v-for` 动态渲染
- [ ] 颜色值使用 CSS 变量，不写死
- [ ] 数量由数据源决定，不写死固定值
- [ ] 后端扩展配置项时，前端无需修改

```java

    }
```
```typescript
}
```

```typescript
// API 请求封装
async function request<T>(config: AxiosRequestConfig): Promise<T> {
  try {
    const response = await axios.request<Result<T>>(config)
    if (response.data.code !== 200) {
      showToast(response.data.message)
      throw new Error(response.data.message)
    }
    return response.data.data
  } catch (error: any) {
    // 网络错误
    if (!error.response) {

    }

    }
    // 其他错误

    showToast(message)
    throw error
  }
}
```

## 十一、页面布局规范

### 11.1 核心原则：禁止页面内随意硬编码布局值

**页面布局必须优先使用 UnoCSS shortcuts、CSS 变量或集中维护的语义化 token，禁止在页面模板和 scoped CSS 中零散硬编码像素值。**

允许在 `frontend/uno.config.ts`、全局 CSS 变量或组件内部有明确设计原因的 scoped CSS 中集中管理尺寸值；页面代码只能引用语义类、变量或 props，不得复制散落的 `w-[317px]`、`p-[23px]`、`min-width: 150px` 等一次性数值。

### 11.2 布局架构

```
┌─────────────────────────────────────────────────────────────┐
│                      Layout.vue                             │
│  ┌─────────────┬───────────────────────────────────────────┐│
│  │             │  .pc-main (padding: 24px)                  ││
│  │  侧边栏      │  ┌───────────────────────────────────────┐││
│  │  240px      │  │  页面容器 (无 padding)                  │││
│  │             │  │  ┌─────────────────────────────────────┐│││
│  │             │  │  │  内容区域 (flex + gap)              ││││
│  │             │  │  └─────────────────────────────────────┘│││
│  │             │  └───────────────────────────────────────┘││
│  └─────────────┴───────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────┘
```

### 11.3 页面容器规范

**禁止事项：**

| 禁止写法 | 问题 | 正确写法 |
|----------|------|----------|
| `min-height: 100vh` | 在 Layout flex 容器内溢出 | 不设置，由内容撑开 |
| `padding: 32px` | 与 Layout 的 padding 重复 | 不设置，使用 Layout 的 padding |
| `max-width: 1200px` | 限制宽度，无法铺满 | 不设置，横向铺满 |
| `margin: 0 auto` | 居中缩小可用空间 | 不设置 |

**正确示例：**

```css
/* PC端容器 */
.pc-xxx {
  display: flex;
  flex-direction: column;
  gap: var(--spacing-lg);
  /* 无 padding、max-width、margin、min-height */
}

/* 移动端容器 */
.mobile-xxx {
  display: flex;
  flex-direction: column;
  padding: var(--spacing-md);
  padding-bottom: 100px; /* 为底部标签栏留空间 */
}
```

### 11.4 UnoCSS 布局 Shortcuts

**核心定位：UnoCSS 是结构与语义化样式工具层，不替代复杂组件的 scoped CSS。**

开发时按以下边界使用：

| 样式类型 | 推荐归属 | 说明 |
|----------|----------|------|
| 页面容器、区块、头部、筛选栏 | UnoCSS shortcuts | 使用 `page-pc`、`section`、`header-row`、`filter` 等语义类 |
| 常规 flex/grid/gap/padding/margin | UnoCSS 原子类或 shortcuts | 减少重复 scoped CSS |
| 字体、颜色、间距 token | UnoCSS theme + CSS 变量 | 继续绑定 `--font-size-*`、`--spacing-*`、`--primary-color` |
| 组件基础态 | UnoCSS shortcuts | 如 `card`、`btn-primary`、`status-active` |
| 复杂响应式、容器查询、动态尺寸 | scoped CSS | 如 `@container`、组件内部 CSS 变量、运行时状态 |
| 运行时业务颜色 | CSS 变量或 inline style | 如分类视觉、涨跌色、主题色 |

**使用原则：**

1. 页面级布局优先使用 UnoCSS shortcuts，不在每个页面重复写 `display:flex`、`gap`、`padding`。
2. 组件内部如果只是常规布局，优先使用 UnoCSS 类；如果涉及容器查询、复杂状态、运行时变量，使用 scoped CSS。
3. 模板中避免堆叠过长原子类。超过 8-10 个原子类且会复用时，应沉淀为 shortcut 或组件 class。
4. 不允许在页面模板中使用 UnoCSS 任意值制造新的硬编码，如大量 `w-[317px]`、`p-[23px]`。确需任意值时必须沉淀到 `frontend/uno.config.ts`、CSS 变量或组件 scoped CSS，并说明设计原因。
5. UnoCSS 的 theme 必须继续复用 CSS 变量，不直接写死项目主色、字号、间距。
6. Vant 组件样式不通过 UnoCSS 强行覆盖；项目已使用 `mode: 'vue-scoped'`、排除 `van-`，应保持共存边界。

**页面级布局：**

| 类名 | 说明 | 等效样式 |
|------|------|----------|
| `page` | 页面容器 | `min-h-screen bg-gray-50` |
| `page-pc` | PC端页面 | `page flex flex-col gap-lg` |
| `page-mobile` | 移动端页面 | `page flex flex-col` |

**区块级布局：**

|------|------|----------|

| `section-sm` | 小间距区块 | `bg-white rounded-lg shadow-sm p-md` |
| `section-flat` | 无内边距区块 | `bg-white rounded-lg shadow-sm` |

**头部布局：**

| 类名 | 说明 | 等效样式 |
|------|------|----------|
| `header-row` | 头部行 | `flex items-center justify-between gap-md` |

| `header-actions` | 操作按钮组 | `flex items-center gap-sm` |

### 11.4.1 UnoCSS 扩展规范

当多个页面或多个组件重复出现同一组样式时，应优先扩展 `frontend/uno.config.ts`，而不是在各页面复制 scoped CSS。

**允许扩展的类型：**

| 类型 | 示例 | 说明 |
|------|------|------|
| 页面级 shortcut | `page-pc`、`page-mobile` | 页面通用骨架 |
| 区块级 shortcut | `section`、`section-sm` | 内容区块 |
| 业务语义 shortcut | `home-card`、`home-price` | 某一业务组件族复用 |
| 工具 rule | `truncate-1`、`break-anywhere` | 小而稳定的原子能力 |
| 容器工具 rule | `container-inline` | 用于声明容器查询上下文 |

**不允许扩展的类型：**

| 类型 | 原因 |
|------|------|
| 单页面一次性样式 | 会污染全局配置 |
| 只服务一个按钮或一个字段的 shortcut | 复用价值低 |
| 包含业务数据值的 class | 运行时数据应走 CSS 变量或 inline style |
| 过度抽象的命名 | 如 `nice-card`、`pretty-text`，语义不清 |

**推荐新增 rules：**

```typescript
rules: [
  ['truncate-1', {
    overflow: 'hidden',
    'text-overflow': 'ellipsis',
    'white-space': 'nowrap',
  }],
  ['break-anywhere', {
    'overflow-wrap': 'anywhere',
  }],
  ['container-inline', {
    'container-type': 'inline-size',
  }],
  ['numeric-tabular', {
    'font-variant-numeric': 'tabular-nums',
  }],
]
```

### 11.4.2 UnoCSS 与 scoped CSS 分工示例

**推荐写法：**

```vue
<template>
  <article class="home-card home-card-hover container-inline flex flex-col gap-sm">
    <div class="flex items-start justify-between gap-sm">
      <span class="home-card-title break-anywhere" :title="product.name">

      </span>

}

```

说明：

**禁止写法：**

```vue
  ...
</article>
```

```vue
<article class="home-card home-card-hover">
  ...
</article>
```

### 11.5 表格布局规范

**核心原则：表格列宽使用百分比，禁止使用固定像素值。**

**问题场景：**

```css
/* ❌ 错误：flex + min-width 累加超宽 */
.table-cell.name { flex: 1.5; min-width: 150px; }
.table-cell.origin { flex: 1; min-width: 100px; }
/* 多列累加后总宽度超出容器，出现横向滚动条 */
```

**正确做法：**

```css
/* ✅ 正确：百分比宽度，总宽度 100% */
.table-cell.name { width: 15%; }
.table-cell.origin { width: 10%; }
.table-cell.specs { width: 20%; }
/* 总计：15+10+20+... = 100% */
```

### 11.9 常见问题与解决方案

**问题 1：页面出现横向滚动条**

原因：表格列宽使用 `flex + min-width`，累加超出容器。

解决：
1. 列宽改为百分比（`width: 15%`）
2. 表格容器添加 `overflow-x: auto`
3. 表头/行添加 `min-width: max-content`

**问题 2：内容不铺满屏幕**

原因：页面容器设置了 `max-width` 或 `margin: 0 auto`。

解决：移除 `max-width` 和 `margin: 0 auto`，让内容横向铺满。

**问题 3：页面底部留白过大**

原因：页面容器设置了 `min-height: 100vh`。

解决：移除 `min-height: 100vh`，由 Layout 控制高度。

## 十三、工程质量门禁规范

### 13.1 核心原则：关键风险必须被拦截

当前项目采用 **8.5主体规范 + 核心风险9.0门禁** 策略：常规研发保持轻量，数据库迁移、鉴权安全、生产配置、构建测试等高风险项必须设置硬性门槛。

质量门禁可以先由人工执行并在 PR / 发布记录中勾选；具备 CI 条件后，应逐步自动化。门禁失败时，不得合并到主分支，不得发布到生产环境。

### 13.2 必跑门禁

| 门禁项 | 执行位置 | 命令或检查方式 | 失败处理 |
|--------|----------|----------------|----------|
| 后端测试 | `backend/` | `mvn test` | 不得合并 / 不得发布 |
| 前端构建与类型检查 | `frontend/` | `npm run build` | 不得合并 / 不得发布 |
| 数据库迁移校验 | `backend/` | 应用启动或 `mvn test` 触发 Flyway 校验 | 不得发布 |
| 生产危险配置检查 | `backend/src/main/resources/application*.yml` 与部署环境变量 | 按 17.2 清单检查 | 不得发布 |
| API 契约一致性 | 后端 DTO / Controller 与前端 `api/`、`types/` | 代码审查 + 构建验证 | 不得合并 |

### 13.3 门禁豁免规则

质量门禁原则上不得跳过。确需临时豁免时，必须同时满足：

1. 记录豁免原因、影响范围、风险等级和补偿措施
2. 明确责任人和补跑时间
3. 数据库迁移、安全配置、生产默认密码、空密钥不得豁免

## 十五、数据库迁移治理规范

### 15.1 Flyway 为正式迁移机制

生产和共享环境以 `backend/src/main/resources/db/migration/` 下的 Flyway 脚本为正式数据库变更来源。`init.sql` 用于初始化和本地基线辅助，不能替代 migration。

**迁移规则：**

1. 新增表、字段、索引、约束、初始化字典项时，必须新增 Flyway migration
2. 已进入共享环境或生产环境的历史 migration 禁止随意修改
3. 需要修正历史问题时，新增后续版本 migration，不回改旧脚本
4. Entity、Flyway migration、`init.sql`、`数据字典.md` 必须保持一致
5. JPA 配置应保持 `ddl-auto: validate`，禁止依赖 Hibernate 自动改表

### 15.2 表结构变更要求

| 变更类型 | 要求 |
|----------|------|
| 新增字段 | 明确类型、默认值、是否允许空、字段说明 |
| 非空字段 | 已有数据必须先回填，再添加 `NOT NULL` 约束 |
| 状态字段 | 使用字典分类，长度默认 `VARCHAR(20)` |
| 金额 / 价格字段 | 使用定点小数类型，禁止使用浮点类型存储金额 |
| 外键字段 | 命名为 `xxx_id`，Entity 中 `@JoinColumn` 必须对应实际列 |
| 唯一约束 | 明确业务唯一性，如编码、用户名、API Key 前缀 |
| 索引 | 高频筛选、排序、关联字段必须评估索引 |

### 15.3 数据修复脚本

数据修复脚本必须包含：

1. 修复目标和影响范围
2. 执行前验证 SQL
3. 修复 SQL
4. 执行后验证 SQL
5. 回滚或补偿方案

## 十六、安全基线规范

### 16.1 认证与会话

- Access Token 与 Refresh Token 必须有明确过期时间
- Refresh Token 必须支持吊销，用户退出、修改密码、禁用账号后必须失效
- H5 使用 `localStorage` 存储 Token 时，必须配合 XSS 防护和敏感页面最小化展示；如引入 HttpOnly Cookie，应同步评估 CSRF 防护
- 前端路由权限只用于体验控制，后端权限校验才是最终安全边界

### 16.2 CORS 与密码策略

- 生产环境 `CORS_ALLOWED_ORIGINS` 必须配置为具体域名，禁止使用全量通配
- 默认用户密码必须通过 `DEFAULT_USER_PASSWORD` 配置，生产环境禁止使用默认弱密码
- 密码策略必须通过 `security.password-policy` 管理，至少包含长度、字母、数字、空白字符限制
- 登录失败、密码修改、账号禁用等高风险操作必须记录操作日志

### 16.3 敏感信息与日志脱敏

以下字段不得明文写入普通日志、前端控制台或导出文件：

| 类型 | 示例 |
|------|------|
| 密码与密钥 | password、JWT_SECRET、API Key secret、加密密钥 |
| 令牌 | Access Token、Refresh Token、Authorization 头 |
| 签名材料 | nonce、signature 原文、完整待签名密钥 |
| 个人敏感信息 | 手机号、邮箱等按业务需要脱敏展示 |

### 16.4 文件上传与导入导出

- 上传文件必须限制大小、类型和存储路径
- 文件名不得直接信任用户输入，应生成安全文件名
- Excel 导入必须校验字段类型、枚举值、必填项和最大行数
- 导出敏感数据必须校验权限，并记录操作日志

### 16.5 API Key 与防重放

- 外部 API 必须校验签名、时间窗、Nonce 和接口权限
- Nonce 在有效期内不得重复使用
- 时间窗默认使用 `API_KEY_TIMESTAMP_WINDOW_SECONDS` 配置
- 授权失败应记录调用日志，但错误信息不得泄露密钥、签名材料和内部实现细节

## 十七、生产配置与发布规范

### 17.1 发布前检查流程

```
1. 确认变更范围
      │
      ▼
2. 执行质量门禁
      │
      ▼
3. 校验 Flyway migration 与数据字典
      │
      ▼
4. 检查生产环境变量与敏感配置
      │
      ▼
5. 备份数据库或确认可恢复点
      │
      ▼
6. 发布应用
      │
      ▼
7. 验证健康检查、登录、核心业务流程
```

### 17.2 生产环境禁止项

| 禁止项 | 风险 | 正确要求 |
|--------|------|----------|
| `spring.jpa.show-sql=true` | 泄露 SQL 与业务数据，影响性能 | 生产关闭，仅排障时临时开启并记录 |
| debug 级别安全日志 | 泄露认证、权限和请求细节 | 生产使用 info/warn，敏感日志脱敏 |
| 默认用户密码 | 账号被撞库或直接登录 | 生产必须设置强 `DEFAULT_USER_PASSWORD` |
| 空 `JWT_SECRET` | Token 可伪造或应用启动异常 | 必须设置高强度随机值 |
| 空 `DB_PASSWORD` | 数据库无保护或连接失败 | 必须通过环境变量配置 |
| 弱 API Key 加密密钥 | 外部接口凭证可被破解 | 必须设置高强度 `API_KEY_ENCRYPTION_KEY` |
| `reset-password-on-startup=true` | 生产密码被启动流程重置 | 生产必须设为 `false` |

### 17.3 回滚要求

- 应用发布必须保留上一版本可回滚包或镜像
- 数据库 migration 默认向前演进，回滚应采用补偿 migration 或数据修复脚本
- 配置变更必须记录变更前后的关键值来源，不记录敏感值明文
- 发布后发现鉴权、迁移、核心业务不可用时，必须优先执行回滚或停用相关功能

## 十八、可观测性与运维规范

### 18.1 健康检查

应用启动后必须能确认以下状态：

| 检查项 | 要求 |
|--------|------|
| 应用进程 | 服务端口可访问 |
| 数据库 | 连接正常，Flyway migration 已完成 |
| Redis | 可用时连接正常；不可用时降级策略符合配置 |
| 外部通知 | Webhook 开启时可验证连通性 |
| 定时任务 | 任务启停状态、最近执行时间可查询 |

### 18.2 日志字段规范

关键请求和业务日志应尽量包含：

| 字段 | 说明 |
|------|------|
| requestId / traceId | 单次请求追踪标识 |
| userId / username | 操作用户 |
| module | 业务模块 |
| operationType | 操作类型 |
| status | 成功或失败 |
| durationMs | 耗时 |
| errorMessage | 脱敏后的错误信息 |

### 18.3 监控与告警

| 场景 | 告警条件 |
|------|----------|
| 应用不可用 | 健康检查连续失败 |
| 接口异常 | 5xx 错误率持续升高 |
| 接口慢请求 | 核心接口耗时超过业务阈值 |
| 数据库慢查询 | 查询耗时持续超过阈值 |
| 定时任务失败 | 价格发布、通知投递等任务失败 |
| 通知积压 | Outbox `PENDING` 或 `PROCESSING` 长时间未处理 |
| 登录异常 | 登录失败次数异常升高 |

### 18.4 运维记录

生产发布、配置变更、数据修复、权限调整、异常恢复必须形成记录，至少包含：时间、操作人、变更内容、影响范围、验证结果和回滚方案。
