### 硬件要求
- 内存：至少 8GB，建议 16GB
- 磁盘空间：至少 20GB 可用空间
- CPU：Intel i5 或更高

#### 后端开发环境
- **Java JDK 25+** - 下载地址：https://adoptium.net/
- **Maven 3.6+** - 下载地址：https://maven.apache.org/

- **Redis（可选）** - 用于缓存加速，系统支持懒加载，Redis 不可用时自动降级为内存缓存：`docker run -d --name redis -p 6379:6379 redis:latest`

#### 前端开发环境
- **Node.js 16+** - 下载地址：https://nodejs.org/
- **Git** - 下载地址：https://git-scm.com/
- **UnoCSS** - 原子化 CSS 引擎（已集成，与 Vant 共存）

### IDE推荐

- **前端**: VS Code 或 WebStorm

## 快速开始

### 1. 克隆项目
```bash
cd E:\ClaudeCodeProject\price-management-system
```

### 2. 数据库初始化

1. 启动MySQL服务
2. 创建数据库：
```sql
CREATE DATABASE IF NOT EXISTS price_management DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE price_management;
```

3. **可选**：导入数据初始化脚本（产品分类和产品数据）：
```sql
-- 执行 backend/src/main/resources/init.sql 文件
source /path/to/init.sql;
```
   - 注意：用户数据由Spring Boot应用启动时的DataInitializer自动初始化，无需手动导入

### 3. 后端项目配置

1. 打开 `backend/src/main/resources/application.yml`
2. 修改数据库连接配置：
```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/price_management?useUnicode=true&characterEncoding=utf8&useSSL=false&serverTimezone=Asia/Shanghai
    username: root
    password: 【敏感-已移除】
    driver-class-name: com.mysql.cj.jdbc.Driver
```

#### Redis 配置（支持懒加载与自动降级）

系统使用 Redis 进行缓存，支持懒加载机制：
- **Redis 可用时**：使用 Redis 分布式缓存
- **Redis 不可用时**：自动降级为内存缓存，不影响应用启动

```yaml
spring:
  data:
    redis:
      host: 10.7.5.175
      port: 6379
      timeout: 5000ms
  cache:
    type: redis
    redis:
      time-to-live: 3600000
```

- 缓存服务：`SysDictService`（字典）、`StyleConfigService`（样式配置）
- TTL：1小时 + 随机偏移（80%-120%）防雪崩
- 降级策略：Redis 连接失败时自动使用 `ConcurrentMapCacheManager`

## 开发流程

### 代码风格规范

#### 后端 Java 代码规范
- 使用 4 个空格缩进
- 变量和方法使用 camelCase
- 类名使用 PascalCase
- 常量使用大写蛇形命名 SNAKE_CASE
- 使用 Lombok 简化代码
- 使用 @Slf4j 进行日志记录

#### 前端代码规范
- 使用 2 个空格缩进
- 变量和方法使用 camelCase
- 组件名使用 PascalCase
- 文件名使用 kebab-case
- 使用 TypeScript 进行类型安全检查
- 使用 ESLint 进行代码检查

#### 禁止硬编码规范

**核心原则：所有编码值的显示名称必须从字典服务动态获取，禁止在代码中硬编码。**

**禁止的硬编码模式：**

| 禁止写法 | 正确写法 | 说明 |
|----------|----------|------|
| `status === 'ACTIVE' ? '启用' : '停用'` | `getStatusLabel(status)` | 状态标签 |
| `<option value="ADMIN">管理员</option>` | `v-for="opt in roleOptions"` | 下拉选项 |
| `{ ADMIN: '管理员', EDITOR: '编辑者' }` | `getRoleLabel(role)` | 角色映射 |
| `currency === 'CNY' ? '¥' : '$'` | `getCurrencySymbol(currency)` | 货币符号 |
| `{ CREATE: '创建', UPDATE: '更新' }` | `getDictValue('change_type', key)` | 变更类型等 |

**规则详解：**

1. **状态值**：`ACTIVE/INACTIVE` 等编码的中文显示名称，必须通过 `getStatusLabel()` 获取
2. **角色值**：`ADMIN/EDITOR/VIEWER` 等角色编码，必须通过 `getRoleLabel()` 获取
3. **下拉选项**：表单中的 `<select>` 选项必须通过 `getDictOptions(category)` 动态渲染
4. **货币符号**：必须通过 `getCurrencySymbol()` 获取
5. **通用字典值**：任何编码到中文的映射必须通过 `getDictValue(category, key)` 获取
6. **字典缓存**：每个页面 `onMounted` 中必须调用 `loadAllDicts()` 确保缓存已加载

**例外情况：**
- API 请求参数中的枚举值（如 `status: 'ACTIVE'`）允许硬编码，这是数据协议
- 后端 Entity 中定义的枚举常量允许硬编码
- CSS 类名中的状态值（如 `:class="status?.toLowerCase()"`）允许硬编码

### PC端与移动端适配规范

#### 响应式断点
- **PC端**：window.innerWidth >= 1024px
- **移动端**：window.innerWidth < 1024px
- `useLayout` 在窗口最小化、页面隐藏或浏览器报告极小 `outerWidth/outerHeight` 时不更新布局宽度，避免最小化过程误触发 PC/移动端布局切换。

#### 页面布局要求

**1. 每个页面必须同时支持 PC 端和移动端布局**

每个页面组件（views 目录下的 .vue 文件）必须包含两套布局：

```vue
<template>
  <!-- PC端布局：屏幕宽度 >= 1024px -->
  <template v-if="isPCLayout">
    <div class="pc-page-layout">
      <!-- PC端专用布局和样式 -->
    </div>
  </template>

  <!-- 移动端布局：屏幕宽度 < 1024px -->
  <template v-else>
    <div class="mobile-page-layout">
      <!-- 移动端专用布局和样式 -->
    </div>
  </template>
</template>

<script setup lang="ts">
// 判断是否为PC布局
const isPCLayout = computed(() => {
  if (typeof window !== 'undefined') {
    return window.innerWidth >= 1024
  }
  return false
})
</script>

<style scoped>
/* PC端样式 */
@media (min-width: 1024px) {
  .pc-page-layout {
    /* PC端专属样式 */
  }
}

/* 移动端样式 */
@media (max-width: 1023px) {
  .mobile-page-layout {
    /* 移动端专属样式 */
  }
}
</style>
```

**2. PC端设计原则**
- 使用更大的间距和字体
- 表单采用网格布局（grid）而非堆叠布局
- 侧边栏或顶部导航
- 数据表格展示（如产品列表）
- 支持鼠标悬停效果
- 按钮和交互元素适合鼠标点击

**3. 移动端设计原则**
- 单列布局为主
- 顶部导航栏 + 底部操作区
- 触摸友好的大按钮（至少44px高度）
- 表单项垂直堆叠
- 使用 Vant 或原生移动端组件
- 卡片式布局展示数据

**4. 不得将移动端样式简单放大作为 PC 端样式**

#### 浏览器最小化兼容规范

- 首页及其他 ECharts 图表必须使用 `useSafeChartAutoresize()` 返回的 `chartAutoresize` 绑定 `vue-echarts` 的 `:autoresize`，页面隐藏或窗口最小化时暂停自动 resize。
- 路由 history 必须通过 `router/index.ts` 的 `createAppHistory()` 创建，不直接在业务代码中调用 `createWebHistory()`；该封装会跳过 Vue Router 在 `document.visibilitychange` 中保存滚动位置的监听，避免部分 Edge/Chrome 环境最小化后立即恢复窗口。
- 禁止在页面隐藏、窗口 blur、resize 或 visibilitychange 回调中调用 `window.focus()`、`history.replaceState()`、`history.pushState()` 等可能重新激活窗口的操作；如必须处理，应先判断 `document.visibilityState !== 'hidden'`。

#### 页面铺满规范

页面内容必须铺满 Layout 提供的右侧展示区域，不得留有明显的空白边距。

**核心规则：**

1. **禁止使用 `max-width` 限制宽度** — PC 端页面容器不得设置 `max-width` 和 `margin: 0 auto`，必须横向铺满可用空间
2. **禁止页面级 padding** — Layout 的 `.pc-main` 已提供 24px 统一 padding，页面内部 PC 容器不得再设置 padding
3. **禁止 `min-height: 100vh`** — 页面渲染在 Layout 的 flex 容器内，使用 `100vh` 会导致内容超出可视区域
4. **使用 flex 布局组织内容** — PC 端容器使用 `display: flex; flex-direction: column; gap: 24px;` 替代子元素的 `margin-bottom`

**正确示例：**

```css
/* 页面根元素 */
.xxx-page {
  background-color: #F5F5F5;
  /* 不要设置 min-height: 100vh */
}

/* PC端容器 */
.pc-xxx {
  display: flex;
  flex-direction: column;
  gap: 24px;
  /* 不要设置 padding、max-width、margin: 0 auto */
}
```

**错误示例：**

```css
/* 以下写法均禁止 */
.pc-xxx {
  padding: 32px;          /* 错误：padding 由 Layout 统一提供 */
  max-width: 1100px;      /* 错误：限制了页面宽度，无法铺满 */
  margin: 0 auto;         /* 错误：居中缩小了可用空间 */
}

.xxx-page {
  min-height: 100vh;      /* 错误：在 Layout flex 容器内会导致溢出 */
}
```

**布局结构说明：**

```
┌──────────┬──────────────────────────────────┐
│          │  Layout .pc-main (padding: 24px) │
│  侧边栏   │ ┌──────────────────────────────┐ │
│  240px   │ │  页面 .pc-xxx (无padding)     │ │
│          │ │  ┌──────────────────────────┐ │ │
│          │ │  │  内容区域（铺满）         │ │ │
│          │ │  └──────────────────────────┘ │ │
│          │ └──────────────────────────────┘ │
└──────────┴──────────────────────────────────┘
```

**新建页面检查清单（补充）：**
- [ ] PC 端容器未设置 `max-width`、`margin: 0 auto`、`padding`
- [ ] 页面根元素未使用 `min-height: 100vh`
- [ ] 子元素间距通过父容器 `gap` 控制，而非子元素 `margin-bottom`
- [ ] 页面在宽屏（1920px+）下仍能铺满整个右侧展示区域

### 菜单规范

#### 系统菜单结构（完整树 + 顶部上下文导航）
```
一级菜单（左侧完整菜单树）
  └── 二级菜单（左侧完整菜单树）
        └── 三级菜单（页面顶部上下文 Tab）
              └── 四级菜单（三级 Tab 点击下拉）
```

**示例：**
```
基础运维
  └── 字典管理（父级菜单，无跳转）
        ├── 产地管理 → /origins
        └── 客户管理 → /customers
```

产品管理默认包含：产品列表 `/products`、价格维护 `/price-maintenance`、预算管理 `/budget-management`、价格查询 `/price-query`。预算管理仅 ADMIN/EDITOR 在菜单中可见。

**交互规则：**
- 左侧菜单必须展示当前用户可见的完整菜单树，支持三级及更深层级。
- 带 `path` 的菜单项点击必须优先执行路由跳转；仅当菜单项无 `path` 且有子菜单时，点击才用于展开/收起。
- 无 `path` 菜单只作为分组，点击只展开/收起，不自动跳转到第一个子菜单。
- 页面顶部不再重复展示一级菜单下的二级入口。
- 当前路由位于三级分组时，顶部展示同组三级 Tab。
- 四级及以后菜单通过点击三级 Tab 后下拉展示；更深层级仍可通过左侧完整树访问。
- 编辑页、详情页等非菜单路由应通过 `route.meta.activeMenu` 回落到所属菜单高亮。
- 左侧菜单点击后必须立即更新选中反馈；菜单数据按当前角色缓存，菜单配置变更时再强制刷新，避免路由切换时重复请求 `/api/menus/visible`。
- 菜单树选中态应由 Layout 预计算 active id 集合传入，子菜单组件不得在每个菜单项渲染时递归扫描整棵子树。

#### 菜单创建流程

**1. 后端 - 数据库 menu_item 表**

在 `init.sql` 中插入菜单数据：
```sql
-- 一级菜单（父级）
INSERT INTO menu_item (id, parent_id, name, path, icon, sort_order, visible, roles, created_time, updated_time)
SELECT 24, 3, '字典管理', NULL, 'dict', 5, TRUE, '["ADMIN","EDITOR"]', NOW(), NOW()
WHERE NOT EXISTS (SELECT 1 FROM menu_item WHERE id = 24);

-- 二级菜单（字典管理的子菜单）
INSERT INTO menu_item (id, parent_id, name, path, icon, sort_order, visible, roles, created_time, updated_time)
SELECT 40, 24, '产地管理', '/origins', NULL, 1, TRUE, '["ADMIN","EDITOR"]', NOW(), NOW()
WHERE NOT EXISTS (SELECT 1 FROM menu_item WHERE id = 40);

INSERT INTO menu_item (id, parent_id, name, path, icon, sort_order, visible, roles, created_time, updated_time)
SELECT 41, 24, '客户管理', '/customers', NULL, 2, TRUE, '["ADMIN","EDITOR"]', NOW(), NOW()
WHERE NOT EXISTS (SELECT 1 FROM menu_item WHERE id = 41);
```

**字段说明：**
| 字段 | 说明 |
|------|------|

### 管理员用户管理接口

关键规则：

- 用户列表中的角色展示读取 `sys_user_role` 多角色关联；`sys_user.role` 仅作为兼容主角色字段。
- 多角色维护必须通过独立的“分配角色”入口调用 `/api/roles/assign/{userId}`，不要混入用户编辑资料弹窗。
- 用户编辑弹窗只维护基础资料、部门、状态和可选新密码；新密码留空表示不修改密码。
- 用户手机号只允许数字，前端输入时过滤非数字，后端保存时再次净化；无手机号时保持空值。
- 管理员重置他人密码使用 `/api/users/{id}/reset-password`，后端只更新密码和 `password_updated_time`，不得因此覆盖用户多角色关联。

### 个人中心与账号运维接口

个人中心新增语义化接口 `/api/profile/**`，旧的 `/api/auth/profile` 与 `/api/auth/password` 保持兼容并委托 `ProfileService`。

关键规则：

- 所有个人中心接口都从认证上下文识别当前用户，不接受前端传入 `userId` 作为授权依据。
- 个人资料只允许修改 `nickname`、`email`、`phone`，角色、部门、状态、权限等管理字段只读。
- 修改密码由后端统一校验：8-32 位、必须包含字母和数字、禁止空白、不能与旧密码或账号信息相同。
- 修改密码成功后撤销当前用户全部 Refresh Token，前端必须清理本地 Token 并跳转登录页。
- `/api/profile/operation-logs` 优先按 `operation_log.user_id` 查询当前用户，兼容历史 `username` 日志。
- 会话管理基于 `refresh_token` 的设备信息字段，接口不返回 Token 原文。
- 登录成功和登录失败都写入 `sys_login_history`，失败原因只记录摘要。
- 个人偏好写入 `sys_user_preference`，不影响全局样式配置。

### 操作日志接口

`GET /api/logs` 返回的日志状态不直接来自数据库 `status` 列。后端以 `responseCode` 与 `errorMessage` 派生中文 `status`：无错误且响应码小于 400 为 `成功`，否则为 `失败`；同时返回 `errorMsg` 兼容前端展示。日志表中的 `username` 保存登录名用于审计追溯，接口返回时会额外补充 `operatorName`，取自 `sys_user.nickname`（当前界面语义为“姓名”），前端用户列应优先展示 `operatorName`。登录接口属于公开接口，记录登录日志时如果当前没有认证上下文，必须使用登录标识兜底写入 `username`。

日志页传给后端的 `startTime` / `endTime` 必须使用本地时间格式 `yyyy-MM-dd HH:mm:ss`，禁止用 `Date.toISOString()` 直接生成筛选时间，否则浏览器会转换成 UTC，导致当前时区的新日志被结束时间过滤掉。

标注 `@OperationLog` 的接口由 `OperationLogAspect` 统一写入操作日志。已有手动调用 `OperationLogHelper` 的接口不要再重复标注，避免同一动作写入两条日志。

### 外部 API 授权管理接口

外部 API 第一期采用“管理端 JWT + 外部端 API Key”的双认证模型：

- `/api/api-keys/**` 和 `/api/api-call-logs/**` 是内部管理接口，仅 `ADMIN` 可通过 JWT 访问。
- `/api/external/v1/**` 是外部调用接口，只接受 API Key 签名认证，不接受 `Authorization`。
- `api-key.enabled` 默认 `false`，启用后也只影响 `/api/external/**`，内部 `/api/**` 不进入 API Key 过滤器。
- `api-key.enabled` 是部署级开关；`sys_style_config.external_api_service_enabled` 是页面运行时开关，允许 ADMIN 在 `/api-keys` 即时暂停/恢复外部 API。
- API Key 的 `rateLimitPerMinute` 和 `dailyLimit` 允许填写 `0`，表示对应维度不限制；前端、DTO 校验和 `ApiRateLimitService` 必须保持一致。
- 所有外部端点必须登记到 `sys_external_api_endpoint`，未登记接口默认拒绝。
- 外部 Controller 使用 `hasAuthority('API_xxx')`，不得授予 `ROLE_ADMIN`、`ROLE_EDITOR`、`ROLE_VIEWER`。
- 外部写入口必须清理请求体里的系统字段（如 `id`、`version`、`createdTime`），避免外部系统覆盖服务端生成字段。
- 外部端点元数据必须维护请求/响应示例、参数 schema 和代码调用提示；前端通过 `externalApiCodeExamples.ts` 生成 Node.js、Java 25、Postman、PowerShell、curl 示例，不能把真实 App Secret 发回后端生成代码。
- 阶段一暂不缓存 API Key 授权元数据，密钥状态和权限变更立即查库生效；`api-key.cache-ttl-seconds` 仅作后续优化预留。
- 阶段一审批申请人使用系统外部申请人占位 `0`，真实来源以外部调用日志 `appId` 追溯；外部应用到内部用户/部门的身份映射放到阶段二。

- PC 端使用“领域页签 + 分类页签 + 左说明/预览 + 右表格”的结构；移动端使用横向页签、说明摘要、可折叠预览和卡片列表。
- `dictCategoryMeta.ts` 必须为可治理分类补充 `helpTitle`、`usage`、`usedIn`、`keyRule`、`valueRule`、`extraValueRule`、`previewType` 和 `examples`，让管理员在维护前能看到用途、规则和影响范围。
- `DictCategoryHelpPanel` 只展示分类元数据和当前分类数量，不直接请求接口。
- `DictCategoryPreview` 优先使用当前分类真实启用项；没有真实数据时才使用元数据中的示例作为空态辅助，不得替代业务页面的字典值解析。
- 受保护分类继续通过 `editableInDictPage=false` 与 `ownerPage` 控制只读和跳转入口，不允许在字典管理页绕过专用配置页面。

**分类视觉配置开发约束：**

- 分类主数据必须来自 `product_category`，禁止用字典项替代分类实体。
- `category_visual_config` 只保存分类视觉附加配置，`dictKey` 推荐使用分类编码，`extraValue` 必须为 JSON。
- `category_visual_custom_combo` 只保存 1 组“我的组合”，固定 `dictKey = my_combo`；当前界面不提供独立保存按钮，避免绕过统一草稿保存模型。
- 视觉配置应优先通过 `categoryVisualPresets.ts` 的组合方案或分组预设生成，保存 `presetId`、`presetVersion`、`customized`，便于后续升级和回溯。
- 方案库包含 5 个业务分组、共 50 套预设；组合方案点击后直接更新未配置分类草稿，不自动保存，最终通过顶部“保存配置”统一生效。
- 色彩需通过分类视觉校验：正文对浅底对比度不低于 4.5:1，主色与白色图标对比度不低于 3:1，光晕透明度控制在 0.12-0.18。
- 首页卡片、列表卡片、ECharts 趋势线必须统一读取分类视觉 CSS 变量或 `useCategoryVisual` 输出，禁止在页面中另行硬编码分类颜色。
- 首页产品列表排序采用两级口径：`product_category.sortOrder` 控制分类分组顺序，`product.sortOrder` 控制分类内产品顺序；产品列表、重点关注指标与重点走势必须保持同源排序。
- 首页重点产品主曲线、重点走势卡片和产品列表迷你走势图必须使用 `/api/products/{productId}/price-trend` 返回的 `currentPrice`、`budgetPrice` 绘制双线；预算线读取 `themeConfig.chartBudgetColor`。表格迷你走势图的 HTML tooltip 挂载到页面顶层，避免被单元格 `overflow` 裁剪。
- 首页 PC 产品列表采用分页表格工作台，必须通过 `/api/products` 分页参数获取数据，禁止拉取全量产品后仅在前端分页；表格搜索、分类筛选、状态筛选、排序变更时重置页码，后端必须组合执行 `keyword`、`categoryId`、`status` 条件，不能让关键词搜索覆盖其他过滤条件。
- 产品管理页 PC 端采用产品列表联动详情侧栏，移动端采用单列产品卡片；列表默认根据容器真实高度自适应分页 `size`，页码较多时必须保留首页、末页、当前页附近页码、省略号和跳页输入。`keyword` 同时匹配产品名称、编码和规格，状态、单位、产地、客户、币种显示必须通过字典服务解析。
- 价格维护页采用与首页产品列表一致的分页工作台；搜索、产品类别筛选、每页条数和翻页必须通过 `/api/products` 分页参数获取当前页产品，价格对照数据通过 `/api/prices/by-date-with-stats` 填充。
- 预算管理页必须调用 `/api/product-budgets`，以产品 + 年份维护年度预算；年份选择不得固定最近年份，必须允许用户直接输入 1900-2999 范围内任意年份并加载对应年度数据。
- 年度预算是预算价唯一业务来源；价格查询、价格维护统计、产品列表、产品详情、外部产品接口和价格走势在日期落入某年度时，只引用 `product_annual_budget(product_id, budget_year)`。产品编辑、产品接口、价格维护和价格审批不得写入产品旧 `budget_price` 字段；未维护年度预算时其它页面显示为空。
- `/api/products/{productId}/price-trend` 必须返回请求范围内完整日期轴；`currentPrice` 只来自已发布正式价格，并从正式价格生效日持续到下一次正式价格或显式到期日；`budgetPrice` 按日期所属年度从 `product_annual_budget` 读取。预算管理、价格查询、产品详情、首页和小程序趋势图都必须允许预算-only 数据独立成线，统计指标只基于正式售价计算。
- 预算管理页右侧年度走势图必须调用 `/api/products/{productId}/price-trend` 获取选中产品自然年数据，图表视觉与 `/price-query` 保持一致：正式价格实线、年度预算虚线、金额轴、日期轴、tooltip 和单价格点圆点。
- 价格维护保存/发布采用双阶段流程：保存调用 `/api/price-drafts/batch-save` 只写当前日期草稿；PC 和小程序发布按钮先读取 `/api/price-drafts/publishable-summary` 展示全系统待发布日期数、批次数和明细数，再调用 `/api/price-drafts/publish-all` 发布全系统所有 `DRAFT` 草稿，不受当前页面日期限制，并写入正式 `price`、`price_history`、同步产品售价并生成一条发布组通知；部分发布重试时必须跳过已发布且存在 `publishedPriceId` 的明细，避免重复写正式价格；`/api/price-drafts/by-date/publish?date=yyyy-MM-dd` 仅作为定时任务、补发或维护入口保留；`/api/price-drafts/{batchId}/publish` 仅作为兼容/单批次维护接口保留；价格查询、首页、外部读接口只读取已发布 `price`。
- PC 端价格发布通知由 `Layout.vue` 统一获取：左侧用户卡片更多菜单提供消息入口，未读时更多按钮由三点图标切换为红色数字角标；采用带随机抖动的未读数轮询 `/api/notifications/unread-count`，页面隐藏时暂停、失败时退避；通知抽屉读取 `/api/notifications/my`，支持全部/未读筛选、单条已读 `/api/notifications/{messageId}/read`、全部已读 `/api/notifications/read-all` 和归档 `/api/notifications/{messageId}/archive`；点击通知采用乐观已读，标记已读失败不得阻断业务跳转。
- 通知列表必须使用 recipient + message 的分页投影查询，禁止在 `getMyNotifications` 中按 recipient 逐条 `findById` 查询消息。外部渠道投递必须先写 `notification_delivery_log=PENDING` 和 `notification_outbox=PENDING`，由 `NotificationOutboxService` 异步领取；worker 必须拆分 claim、Provider send、result 三段事务，Provider 调用不得持有长事务；Provider 未配置、用户关闭偏好、免打扰等降级结果写入投递日志，不得回滚价格发布等业务事务。
- 通知偏好通过 `/api/notifications/preferences` 管理，站内通知 `IN_APP` 是可靠底座，不允许被用户关闭；通知类型和渠道必须校验 `notification_type`、`notification_channel` 启用字典；外部渠道显示值必须通过 `notification_channel`、`notification_delivery_status`、`notification_outbox_status` 等字典分类获取。普通外部通知命中免打扰时应延迟 Outbox `nextRetryTime`，URGENT 可绕过并记录原因。
- 小程序订阅消息通过 `MINI_PROGRAM` Provider 接入 Outbox，PC `/notifications` 是唯一发布入口；小程序通知页是订阅授权主入口，我的页只保留快捷入口，两个页面必须复用 `useMiniProgramSubscription`，不得复制授权上报逻辑。小程序端只在用户点击明确授权按钮后调用 `uni.requestSubscribeMessage`，模板较多时按微信单次限制分批请求，并通过 `/api/notifications/mini-program/subscriptions` 上报授权结果。后端只使用当前登录用户 ID 和 `sys_user.wechat_openid`，不得信任客户端传入用户 ID。
- 微信小程序登录页提供三个固定环境：本地测试 `http://127.0.0.1:8080` 仅用于开发者工具模拟器；内网正式环境 `http://10.7.5.175:32801` 使用独立 HTTP 端口；公网正式环境 `https://price.jlmining.com:32080` 使用独立 HTTPS 端口。真机禁止应用本地测试；内网正式环境使用 HTTP/IP 时需要真机调试开启“不校验合法域名”。登录页初始化时必须先确定网络环境，再请求主题配置和执行登录，避免请求落到不同服务器。
- 小程序产品详情属于业务展示页面，不展示内部产品编码；`originIds`、`customerIds` 中的编码必须通过 `useDict` 转换为产地和报价适用客户中文名称，禁止直接回显编码。
- 小程序产品详情价格走势必须使用 `/api/products/{productId}/price-trend` 返回的每日 `currentPrice` 与 `budgetPrice` 绘图；预算价格缺失时不得使用当前预算价兜底，应显示为空。趋势图必须提供日期刻度和触摸选点详情，选点详情放在时间范围按钮上方以避免手指遮挡；最高/最低/平均/最新统计只基于售价计算。小趋势图也必须支持预算线和单价格点圆点，不能过滤掉 `currentPrice` 为空但 `budgetPrice` 存在的日期。
- PC 端价格走势图范围统一从 `chart_range` 字典读取 30天、180天、12个月；产品详情查看指定年份时，必须向 `/api/products/{productId}/price-trend` 同时传入自然年的 `startDate`、`endDate`，不得用固定 365 天代替自然年。
- PC 产品详情、价格查询页与小程序产品详情必须通过 `/api/products/{productId}/price-years` 动态获取该产品真实录入年份，不得按固定最近年数或产品创建年份生成选项。选择年份后自动切换到 12个月，并通过 `startDate=YYYY-01-01`、`endDate=YYYY-12-31`（当前年截至当天）查询自然年数据。
- PC 产品详情页头提供“价格查询”按钮并直接跳转 `/price-query`；历史快照日期由日期控件切换，不设置独立“返回当前”按钮。
- 小程序统一请求 Loading 必须兼容微信原生提示通道竞态：`hideLoading` 的“toast can't be found”失败需要安全忽略；已有页面级或组件级加载态的请求应传入 `showLoading: false`，避免全局 Loading 与局部状态重复。
- 小程序价格维护页必须与首页一样锁定视口宽度：根容器、纵向 `scroll-view`、产品卡片及固定底栏使用 `width: 100%`、`box-sizing: border-box` 和横向溢出裁切；Grid/Flex 子项使用 `min-width: 0`，避免长名称或金额撑宽页面造成真机左右晃动。
- PC `/notifications -> 渠道配置` 只维护小程序订阅消息基础运行配置：启用状态、AppID、AppSecret、默认跳转页、接口地址和超时。`NotificationMiniProgramRuntimeConfigService` 优先读取 `notification_mini_program_template` 中的 `ACTIVE` 模板，旧 `notification_channel_config.config_json` 模板仅作为兼容兜底；仅当数据库没有该渠道配置时，才允许用 `notification.mini-program.*` 作为初始化来源。AppSecret 使用 `ApiKeySecretService` AES-GCM 加密保存，依赖 `API_KEY_ENCRYPTION_KEY`，任何响应、日志和导出不得回显明文。
- PC `/notifications -> 小程序模板` 是订阅消息模板唯一运维入口。模板版本状态为 `DRAFT/TESTING/ACTIVE/DISABLED`，同一通知类型只允许一个 `ACTIVE` 模板；发布新模板会停用旧模板并触发资格快照重建。模板字段映射必须使用可编辑键值结构保存语义字段到微信字段编号，字段编号格式需通过后端校验；模板 ID 变化后用户必须重新授权。
- 渠道配置编辑时允许回写非敏感 AppID；AppSecret 禁止解密回传浏览器，只返回是否已配置、来源和脱敏 SHA-256 指纹用于确认是否发生替换。默认跳转页和模板跳转页必须从 `notification_mini_program_page` 启用字典项选择，后端保存时同步校验，禁止提交字典外路径。
- 小程序渠道状态必须区分保存状态与投递就绪状态：无有效启用项、AppID、AppSecret 或模板时为 `NOT_CONFIGURED`；已保存部分配置但尚未满足“启用 + 凭据 + 完整模板”时为 `DEGRADED`；全部满足时为 `OK`。不得将部分配置统一显示为“未配置”。
- `MINI_PROGRAM` Provider 必须读取 `notification.mini-program.*` 或 PC 渠道配置，AppSecret、模板 ID 和字段映射不得硬编码。模板必须按 `notification_type` 分类配置；微信订阅消息跳转到 `pages/notifications/index` 时必须追加 URL 编码后的 `messageId`，便于小程序自动打开并标记对应站内通知。未配置、未绑定 openid、未授权记录 `SKIPPED`；临时微信错误记录 `FAILED` 并允许 Outbox 重试；模板无效、字段错误、用户拒绝等永久错误记录 `SKIPPED`，用户拒绝/授权失效时同步清空本地授权次数。
- 小程序 AppID、AppSecret 和订阅消息模板 ID 的来源是微信公众平台小程序后台，不是本系统自动生成。`application.yml` 不得预置具体 AppID 或正式模板 ID；AppID、模板 ID 和字段映射通过环境变量或 PC 渠道配置维护，`WECHAT_MINI_APP_SECRET` 只能通过环境变量或密钥管理系统注入。PC `/notifications` 只承担发布和配置诊断职责，最多展示“已配置/未配置”、脱敏 ID、模板字段映射、最近错误和授权覆盖情况；严禁在前端页面、普通日志或导出文件中明文展示 AppSecret。
- 通知二期业务接入统一使用 `NotificationCreateCommand` + `NotificationService.create(command)`；审批待办、任务失败、外部 API 告警、导入导出完成和系统公告不得直接写 `notification_message`、`notification_recipient`、`notification_delivery_log` 或 `notification_outbox`。
- 核心业务触发通知时必须通过 `NotificationEventService` 在主事务提交后派发，并由独立事务创建通知；通知失败不得回滚核心业务，主事务回滚时不得生成通知。
- 通知创建必须保留站内可靠底座：即使业务方只传外部渠道，`NotificationService` 也必须自动补齐 `IN_APP`，确保用户侧站内列表可追溯；该规则必须有单元测试保护。
- 通知三期观测接口包括 `/api/admin/notifications/dashboard`、`/api/admin/notifications/providers/health`、`/api/admin/notifications/throttle-rules`；Provider 健康状态显示必须通过 `notification_provider_health_status` 字典获取，聚合频控规则来自 `notification_frequency_rule` 字典。
- 用户侧实时增强使用 `/api/notifications/events` SSE 轻事件流，只推送 `connected`、`unreadCountChanged`、`newNotification`；PC 前端使用 fetch stream 携带 Bearer Token，SSE 断开或页面隐藏时必须回退/恢复轮询，不通过 URL 传 token。
- Spring Security 必须放行框架内部的 `ASYNC`、`ERROR` dispatcher；SSE 初始请求仍由 JWT 和 Controller 角色权限保护，避免流超时或连接结束后因异步续分派缺少认证上下文触发 `response is already committed`。
- uni-app 通知入口只承载用户侧轻量闭环：通知页展示未读摘要、小程序订阅状态、模板授权状态、全部/未读筛选、全部已读、归档和价格查询跳转；订阅消息点击进入通知页时可通过 `messageId/id` 参数定位并打开对应通知。我的页展示未读角标和订阅快捷入口；不得在移动端提供 Provider 配置、投递日志或失败重试。
- Webhook Provider 通过 `NotificationWebhookProperties` 读取 `NOTIFICATION_WEBHOOK_ENABLED`、`NOTIFICATION_WEBHOOK_URL`、`NOTIFICATION_WEBHOOK_SECRET`、`NOTIFICATION_WEBHOOK_TIMEOUT_MS`；调用必须携带 `delivery-{notification_delivery_log.id}` 幂等键，未配置、超时、非 2xx 和异常均只更新投递日志，不影响业务事务提交。
- ADMIN 通知管理页 `/notifications` 的类型、优先级、业务类型、渠道、投递状态、公告状态和目标角色展示必须通过 `useDict` 获取；新增公告表单、通知筛选、投递日志和重试入口禁止硬编码中文枚举标签。
- ADMIN 通知管理页投递日志在详情面板内分页展示，并支持关键字、渠道和投递状态筛选；切换通知、搜索或重置筛选时必须重置到第一页，避免长日志撑高工作台布局。
- ADMIN 通知管理页收件人清单必须使用 `/api/admin/notifications/{id}/recipients` 返回的 `nickname` / `username` 展示人名；`readStatus` 只用于已读/未读汇总，不在单个收件人标签中展示。
- 小程序覆盖率接口的 `roles` 参数使用逗号分隔字符串，由后端显式拆分和枚举校验；不得依赖 Spring 对 `List<Enum>` 的隐式转换。订阅异常处理使用用户级 `notification_mini_program_resolution`，确保未绑定 OpenID 的用户也能记录处理状态。
- 小程序订阅管理的聚合行状态筛选必须通过 `notification_mini_program_eligibility` 与 `sys_user` JOIN 实现数据库分页，禁止回退到全量 ACTIVE 用户内存过滤。资格快照只用于管理查询，Provider 投递前仍以原始授权记录为准；授权次数消费必须使用数据库条件更新或等价锁/预占机制，临时发送失败要释放预占，授权失效要同步清零；新增影响 OpenID、授权次数或模板配置的写操作时必须同步触发快照刷新。
- 测试投递必须使用 `NotificationService.createTestDelivery` 隔离链路：只创建目标外部渠道投递，收件记录归档、`is_test=true`，不进入站内通知列表、不参与聚合和用户偏好延迟；执行前端必须明确提示会真实调用外部渠道并消耗授权。
- 操作日志和投递错误入库前必须使用统一敏感字段脱敏；配置保存禁止记录请求参数，Provider 异常不得把 AppSecret、access_token 或带密钥 URL 原样写入日志和数据库。
- 通知管理 API 使用按钮级权限码：`notification:view`、`notification:retry`、`system-notice:create`、`system-notice:cancel`、`system:setting`。登录和刷新令牌必须把用户权限码写入 JWT，`JwtAuthenticationFilter` 将权限码加入 Spring Security authorities，前端按钮显隐与后端 `hasAuthority(...)` 必须读取同一份动态权限集合，禁止仅因用户角色为 ADMIN 就在前端绕过权限集合。权限迁移或角色授权变化后，通知管理页需刷新 access token，使 JWT authority 与数据库授权同步。
- 系统公告撤回或过期后，必须同步处理对应通知消息的用户可见性；用户侧通知列表、未读数和全部已读口径统一排除已归档或已过期通知。
- Outbox worker 调用外部 Provider 前必须重新检查消息过期时间和收件记录归档状态；聚合通知每次更新必须增加 `event_count` 并生成本次事件对应的渠道投递记录。
- ADMIN 投递重试接口只允许重试 `FAILED` 状态的外部渠道投递；`IN_APP`、`SUCCESS`、`PENDING`、`SKIPPED` 必须拒绝，避免污染成功审计记录或重复外部推送。
- 旧正式价格写入接口 `/api/products/{productId}/prices`、`/api/prices/{id}` 仅作为兼容或特殊维护入口，允许 `ADMIN/EDITOR` 调用，必须携带或默认写入 `source=FORMAL_PRICE_MAINTENANCE` 作为审计来源；价格维护页不得调用这些旧接口。
- 价格发布当前不触发审批；仅预留 `PRICE_PUBLISH` 审批类型和草稿状态，默认不启用、不在前端暴露启用入口。
- 价格维护页必须保留拖拽调整产品顺序能力；排序列只显示拖拽手柄，不显示文字表头；拖拽过程中必须提供产品浮层预览和插入线落点反馈，拖拽落位后立即调用 `/api/products/batch-sort` 保存当前列表产品的 `sortOrder`，并触发 `product-sort-updated` 事件刷新 Home，不能等同于价格保存按钮。
- 价格查询页必须通过 `/api/price-query` 做后端分页聚合，导出必须调用 `/api/price-query/export` 并复用同一组筛选参数；页面只读，不提供新增、编辑、删除入口。默认日期与首页/价格维护一致为昨日，首次加载优先选中第一条当日有报价的产品。
- 价格查询页表格列按“产品名称、近期价格、预算价格、较预算”展示；产地来自 `originIds` 和字典服务，以胶囊形式融入产品名称单元格，规格作为产品名称单元格副信息展示。“近期价格”展示查询日仍有效的最后一次正式价格，“预算价格”展示该最新有效价格日所属年度预算，“较预算”使用 `budgetChangeAmount`。
- 价格查询页右侧价格指标洞察必须按启用的 `price_metric_group` 字典动态分组，并从启用的 `price_metric` 字典读取指标名称、排序、分组、`valueType` 与说明；稳定 Key 禁止修改和删除，可通过停用控制展示。指标值由 `/api/price-query` 返回，不得在前端根据趋势数据重复推导；月均、环比、同比及预算均以每个产品的最新有效价格日为基准。
- 价格查询页分页默认提供可重新选择的“自适应”模式：宽屏左右分栏按表格真实可用高度在 5-12 条之间计算；宽度不超过 1180px 的上下堆叠桌面布局固定降级为 10 条，避免容器被当前数据行数撑开后产生自锁；移动端固定降级为 5 条。
- `home_layout` 仅保留首页仍消费的展示参数：`card_columns`、`featured_product_count`、`product_list_mode`、`product_table_page_size`；`layout_mode`、`card_columns_mobile`、`show_trend_chart`、`show_alerts` 不再作为首页渲染开关。
- `home_layout.featured_product_count` 控制首页重点产品数量，前后端必须限制在 1-4，保持与首页 2×2 重点产品区一致。
- `home_layout.product_list_mode` 控制首页产品列表展示模式，`home_layout.product_table_page_size` 控制默认每页条数，二者由样式设置统一保存。
- `home_layout.product_list_mode` 的取值为 `table` / `cards` / `auto`：PC 宽屏优先表格，中等宽度或自动模式下可降级为卡片；样式设置预览必须同步表达当前模式和每页条数。
- Home 页面主内容必须自适应可用宽度，页面级禁止横向滚动；宽度不足时产品列表应切换为卡片或压缩列宽，不能依赖固定 `min-width` 撑开页面。
- 首页摘要统计接口 `/api/home/summary` 应返回产品总数、今日更新、覆盖品类、价格异动相关字段，前端 `SummarySection` 只负责展示，不重复散落业务统计口径。
- 首页计算分类顺序时必须优先使用最新分类列表 `categoryMap` 中的 `sortOrder`，产品响应内嵌的 `product.category.sortOrder` 只能兜底，防止分类批量排序保存后首页读取旧数据。
- 样式设置“首页排序”页签统一控制首页组件显隐与上下顺序，并通过 `/api/home/product-order` 动态加载启用分类和启用产品；分类/产品排序草稿随顶部“保存配置”统一提交，保存时调用 `/api/categories/batch-sort` 与 `/api/products/batch-sort`，并触发 `category-sort-updated`、`product-sort-updated` 事件刷新首页。
- 首页产品信息展示产地时必须解析 `product.originIds` 并通过 `getOriginName()` 获取 `origin` 字典名称；未配置产地时不显示产地行、不显示“未设置”占位，保持卡片视觉层级紧凑。

## 常见问题

### 1. 端口被占用
如果 8080 或 5173 端口被占用，可以修改配置：

#### 后端端口修改
修改 `application.yml`：
```yaml
server:
  port: 8081
```

#### 前端端口修改
修改 `vite.config.ts`：
```typescript
server: {
  port: 5174
}
```

### 2. 数据库连接失败
检查以下几点：
- MySQL 服务是否正在运行
- 用户名和密码是否正确
- 数据库名称是否存在
- 防火墙是否允许连接

### 3. 前端无法访问后端 API
检查：
- 后端是否正在运行
- 后端端口是否正确
- CORS 配置是否正确

### 4. Flyway 迁移校验失败
如果后端启动时报 `Migration checksum mismatch`，说明某个已执行过的迁移文件被修改。历史迁移文件执行后应保持不变，后续数据库结构或初始化数据调整必须新增 `Vxx__*.sql` 迁移文件。开发环境确认历史文件已恢复后可执行 Flyway repair；生产环境必须先备份数据库并确认迁移文件来源一致。

### 5. 本地 Tomcat 临时目录权限失败
如果后端启动时报 `Existing directory ... Temp ... is not owned by ...`，优先使用 `dev` 配置中的 `server.tomcat.basedir=./target/tomcat`。如需指定独立目录，可设置环境变量 `TOMCAT_BASEDIR`，例如 `E:\tmp\price-management-tomcat`。

## API 版本管理规范

### API 版本化策略

当 API 需要不兼容变更时，采用 URL 版本化：

```
/api/v1/products  (当前版本)
/api/v2/products  (新版本)
```

### 版本升级流程

1. **保留旧版本**：旧版本 API 继续服务至少 6 个月
2. **并行运行**：新旧版本同时运行，逐步迁移流量
3. **明确废弃**：通过响应 Header 提示新版本地址
4. **完全迁移**：旧版本无流量后下架

### API 兼容性原则

| 变更类型 | 是否兼容 | 示例 |
|----------|----------|------|
| 新增字段 | ✅ 兼容 | 响应新增 `newField` |
| 新增可选参数 | ✅ 兼容 | `GET /products?newParam=xxx` |
| 修改字段名 | ❌ 不兼容 | `oldName` → `newName` |
| 删除字段 | ❌ 不兼容 | 移除 `deprecatedField` |
| 修改字段类型 | ❌ 不兼容 | `String` → `Number` |

## 代码注释规范

### 注释原则

1. **说明 WHY，而非 WHAT**：代码本身应该足够清晰表达"做什么"，注释应解释"为什么这样做"
2. **保持注释与代码同步**：修改代码时必须同步更新相关注释
3. **避免冗余注释**：不要注释显而易见的代码
4. **使用标准格式**：统一使用 Javadoc（Java）和 JSDoc（TypeScript）格式

### 后端 Java 注释规范

#### 类级别注释

每个类必须有类级别的 Javadoc 注释，说明：
- 类的职责和功能
- 关键设计决策（如有）
- 使用示例（如非显而易见）

**Token 刷新流程：**

1. 请求返回 401 → 前端拦截器捕获
2. 检查是否有 Refresh Token
3. 调用 `/api/auth/refresh-token` 获取新 Token
4. 刷新成功 → 重试原请求
5. 刷新失败 → 跳转登录页

```
│  分布式缓存          │ 内存缓存（单实例）                    │
├─────────────────────┴─────────────────────────────────────┤
│  缓存类型          │ TTL策略              │ 缓存场景         │
├───────────────────┼─────────────────────┼──────────────────┤
│  字典数据          │ 1小时 + 随机偏移      │ SysDictService   │

└─────────────────────────────────────────────────────────────┘
```

**懒加载机制：**
- 应用启动时不强制连接 Redis
- 首次使用缓存时检测 Redis 可用性
- Redis 不可用时自动切换为内存缓存

**随机 TTL 防雪崩：**
- 基础 TTL × (80% ~ 120%)
- 避免大量缓存同时过期

所有敏感配置通过环境变量管理，禁止硬编码：

| JWT 密钥 | JWT_SECRET | SecurityProperties |
| 默认用户密码 | DEFAULT_USER_PASSWORD | SecurityProperties |
| 外部API开关 | API_KEY_ENABLED | ApiKeyProperties |
| 外部API Secret加密主密钥 | API_KEY_ENCRYPTION_KEY | ApiKeyProperties |
| 外部API Secret主密钥版本 | API_KEY_ENCRYPTION_KEY_VERSION | ApiKeyProperties |
| 外部API时间戳窗口 | API_KEY_TIMESTAMP_WINDOW_SECONDS | ApiKeyProperties |
| 外部API Nonce TTL | API_KEY_NONCE_TTL_SECONDS | ApiKeyProperties |
